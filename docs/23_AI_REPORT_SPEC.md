# AI 세션 리포트 — 구성 설계

세션이 끝났을 때 AI가 무엇을 어떤 순서로 말할 것인가. 그리고 그 말이
지켜야 하는 선은 무엇인가.

이 문서는 **구성 설계**입니다. 구현 전에 목차를 확정하려고 씁니다.
현재 계약은 `src/features/ai-report/contract.ts`, 파이프라인은
`api/ai-report-*.ts` 에 있습니다.

---

## 0. 먼저 — 이 설계를 좁히는 두 개의 벽

### 벽 1. 금칙어는 이미 런타임에 걸려 있습니다

```js
const UNSAFE_REPORT_TERMS = /진단|치료|처방|질환|통증|거북목|정상\s*자세|자세\s*교정/
```

`isSafeAiSessionReport()` 가 이 정규식에 걸리는 리포트를 **버립니다.**
"자세 교정 코멘트"를 그대로 쓰면 리포트가 서버에서 거부됩니다.

이건 우회할 대상이 아니라 지켜야 할 선입니다 — `AGENTS.md` 의 의료 판정
금지, 자세 점수 금지가 같은 뿌리입니다. 우리는 물리치료사가 아니고,
웹캠 한 대로 임상 지표를 잴 수도 없습니다.

### 벽 2. 서버는 집계 숫자만 받습니다

영상·프레임·랜드마크·좌표는 브라우저를 떠나지 않습니다.
지금 나가는 것은 8개 숫자뿐입니다.

**이 선은 리포트를 좁히지 않습니다.** 뒤에서 보듯 축별 집계는 좌표가
아니라 숫자이고, 그것만으로도 지금보다 훨씬 할 말이 많아집니다.

## 1. 근거 — 무엇을 말할 것인가

### OSHA (Computer Workstations eTool, Positions)

중립 자세를 이렇게 정의합니다.

> "Head is level, forward facing, and balanced. Generally it is in-line with the torso."
> "Shoulders are relaxed and upper arms hang normally at the side of the body."
> "Elbows stay in close to the body and are bent between 90 and 120 degrees."

그리고 **이 문서에서 가장 중요한 한 줄**:

> "working in the same posture or sitting still for prolonged periods is not healthy"

OSHA 는 이 절에서 **구체적인 휴식 간격을 제시하지 않습니다.** 대신 자세를
바꾸라고 합니다. 우리도 "N분마다 쉬세요" 라고 단정하지 않습니다.

### 임상 연구는 빌려 오지 않습니다

전방 두부 자세(FHP) 연구는 craniovertebral angle 을 재고 도수치료·운동
중재를 비교합니다 (예: Cho et al., *BMC Musculoskelet Disord* 18:525, 2017,
[doi:10.1186/s12891-017-1889-2](https://doi.org/10.1186/s12891-017-1889-2) —
흉추 가동 운동군이 6주 시점 CVA·경부 신전에서 유의하게 개선).

**우리는 CVA 를 재지 않습니다.** 웹캠 정면에서 나오는 것은 개인 기준 대비
편차이지 각도 진단이 아닙니다. 이 문헌은 "우리가 하지 않을 일"의 경계를
확인하는 용도입니다. 리포트에 임상 어휘를 넣으면 안 되는 이유이기도 합니다.

*(문헌 출처: PubMed)*

### 그래서 리포트의 논지는 이렇게 뒤집힙니다

| 흔한 자세 앱 | Deskfit |
|---|---|
| "당신의 자세는 나쁩니다" | 정답 자세를 제시하지 않습니다 |
| 점수 72점 | 점수를 매기지 않습니다 |
| "거북목을 교정하세요" | **"한 자세로 14분을 버텼어요"** |
| 임상 지표 흉내 | 내 기준 대비 변화만 |

**교정 코멘트는 몸이 아니라 환경과 행동을 향합니다.** 이게 금칙어를 피하는
꼼수가 아니라, 근거상 더 맞는 말입니다 — OSHA 가 말하는 위험은 자세의
'틀림'이 아니라 '정지'입니다.

## 2. 지금 보낼 수 있는 것 vs 보낼 수 있게 된 것

### 지금 (8개)

`plannedMinutes` `elapsedMinutes` `detectableMinutes` `awayMinutes`
`recoveryOpportunities` `recoveries` `bestCombo` `status`

이걸로 쓸 수 있는 문장은 "25분 중 21분 앉았고 회복 4번" 이 전부입니다.
**무엇이 흔들렸는지 말할 수 없습니다.**

### 새 엔진이 이미 프레임마다 들고 있는 것

판정 엔진은 매 프레임 11개 축의 편차를 계산합니다
(`facePitchRatio`, `earEyeRatio`, `shoulderSpan`, `headDistanceCm`,
`headPitchDeg`, `shoulderTiltRatio`, …). 지금은 투표에만 쓰고 버립니다.

### 더할 입력 (제안) — 전부 집계, 좌표 아님

| 필드 | 예 | 왜 필요한가 |
|---|---|---|
| `topAxis` | `"headDistanceCm"` | 이번 세션에 **가장 자주 문턱을 넘은 축** |
| `topAxisShare` | `0.62` | 그 축이 전체 이탈의 몇 할이었나 |
| `secondAxis` | `"shoulderTiltRatio"` | 두 번째 축 (한 가지 원인만 말하면 틀립니다) |
| `holdLongestMin` | `14` | **상태가 한 번도 안 바뀐 최장 구간** ← OSHA 근거의 핵심 |
| `stateChanges` | `9` | 자세를 바꾼 횟수 |
| `phaseGood` | `[0.9, 0.7, 0.4]` | 세션을 3등분한 구간별 good 비율 |
| `recoveryMedianSec` | `18` | 회복까지 걸린 시간의 중앙값 |
| `calibratedMinutesAgo` | `4320` | 기준을 맞춘 지 얼마나 됐나 |
| `sensitivity` | `"default"` | 사용자가 손잡이를 어디 뒀나 |

`phaseGood` 이 특히 중요합니다. **"후반에 무너진다"** 는 이 제품이 할 수
있는 가장 유용한 관찰인데, 지금 스키마로는 표현할 방법이 아예 없습니다.

> 개인정보 판단 — 이 값들은 전부 세션 하나에 대한 **스칼라 집계**입니다.
> 좌표도, 시계열도, 프레임도 아닙니다. 이미 나가고 있는 `recoveries` 와
> 같은 성격이라 `docs/14_DATA_PRIVACY_SECURITY.md` 의 경계를 넘지 않습니다.
> 축 이름은 코드 상수이고 신체 치수가 아닙니다.

## 3. 리포트 목차

**다섯 칸. 위에서 아래로 읽으면 끝나고, 중간에 멈춰도 손해가 없습니다.**
각 칸은 하나의 질문에만 답합니다.

```
┌─ 1. 한 줄                    오늘 나는 어땠나        (읽는 데 2초)
├─ 2. 오늘의 숫자 3개          무슨 일이 있었나        (7초)
├─ 3. 무엇이 흔들렸나          왜 그랬나              (15초)
├─ 4. 다음 세션 한 가지        그래서 뭘 하나          (10초)
└─ 5. 더 물어보기              대화로 이어짐          (선택)
```

세션이 끝난 사람은 지쳐 있습니다. **1번만 읽고 닫아도 세션이 완결되게**
설계합니다. 3·4번은 궁금한 사람만 내려갑니다.

---

### 1 · 한 줄 (`headline`, 48자)

오늘을 한 문장으로. **숫자를 넣지 않습니다** — 숫자는 2번 칸의 일입니다.

- 완주: `끝까지 앉아 있었어요`
- 후반 붕괴: `후반에 조금 흐트러졌어요`
- 중단: `오늘은 12분에서 멈췄어요`
- 첫 세션: `첫 세션을 끝냈어요`

> 금지: 평가어(`잘했어요`/`아쉬워요`). 칭찬은 다음에 또 받으려고 앉게
> 만들지만, 못 받은 날 앉지 않게도 만듭니다.

---

### 2 · 오늘의 숫자 (`stats`, 3칸)

한 줄에 셋. **점수는 없습니다.**

| 칸 | 값 | 왜 이 셋인가 |
|---|---|---|
| 앉은 시간 | `21분 / 25분` | 이 제품이 실제로 파는 것 |
| 잰 시간 | `18분` | 자리를 비운 시간은 뺍니다 — 정직 |
| 돌아온 횟수 | `4번` | 유일하게 **늘어날수록 좋은** 숫자 |

"돌아온 횟수"가 세 번째인 이유: 앞의 둘은 오래 앉으면 커지는 값이라
성실함만 말합니다. 세 번째는 **흐트러졌다가 돌아온 것**을 세므로,
흐트러짐 자체를 실패로 만들지 않습니다.

---

### 3 · 무엇이 흔들렸나 (`observations`, 최대 2개)

**여기가 새로 생기는 칸이고, 리포트의 존재 이유입니다.**

각 관찰은 `{ 사실, 해석 }` 두 조각입니다. 사실은 숫자에서 나오고,
해석은 AI가 씁니다. 사실과 해석을 섞지 않아야 사용자가 어디까지가
측정이고 어디부터가 의견인지 압니다.

**관찰 1 — 축 (무엇이)**
```
사실   이번 세션 이탈의 62%가 "화면과의 거리"였어요
해석   집중이 붙을수록 화면 쪽으로 다가가는 흐름이 보여요
```

**관찰 2 — 시간 (언제)**
```
사실   한 번도 자세를 바꾸지 않고 14분을 앉아 있었어요
해석   후반 8분에 이탈이 몰린 건 그 앞의 정지와 이어져 보여요
```

축 이름은 사람 말로 옮깁니다. 세션 화면의 판정 배지와 **같은 표현을
씁니다** — 세션에서 "화면에 가까워졌어요"를 본 사람이 리포트에서
"headDistanceCm"을 보면 두 화면이 다른 제품이 됩니다.

| 축 | 리포트 표현 |
|---|---|
| `headDistanceCm`, `faceScaleRatio` | 화면과의 거리 |
| `headPitchDeg`, `facePitchRatio`, `earEyeRatio` | 고개 각도 |
| `shoulderTiltRatio` | 어깨 높이 |
| `shoulderSpan` | 몸 전체가 앞으로 |
| `lateralOffsetRatio`, `torsoLean` | 좌우 쏠림 |

> **관찰이 없으면 이 칸을 통째로 비웁니다.** 표본이 적거나(짧은 세션)
> 축이 고르게 흩어졌으면 지어내지 않습니다. 없는 패턴을 만들어 내는 것이
> 이 기능이 신뢰를 잃는 가장 빠른 길입니다.

---

### 4 · 다음 세션 한 가지 (`nextAction`)

**하나만.** 셋을 주면 아무것도 안 합니다.

```
제목    의자를 한 뼘 뒤로
방법    다음 세션 시작할 때 등받이에 등을 붙이고 시작해 보세요
근거    이번 세션 이탈의 62%가 화면과의 거리였어요
```

`근거` 줄이 3번 관찰을 그대로 인용합니다 — 제안이 어디서 나왔는지
보이면 따를 이유가 생깁니다.

제안은 **환경과 시작 조건**을 향합니다. 몸을 어떻게 하라고 말하지
않습니다.

| 관찰된 축 | 제안의 방향 |
|---|---|
| 화면과의 거리 | 의자·모니터 위치, 시작할 때의 거리 |
| 고개 각도 | 모니터 높이, 노트북 받침 |
| 어깨 높이 | 팔걸이 높이, 마우스 위치 |
| 오래 정지 | 세션 길이를 25분→15분 두 개로 |

마지막 줄은 OSHA 가 직접 뒷받침합니다 — *"sitting still for prolonged
periods is not healthy"*. **정지를 깨는 제안은 자세를 판정하지 않고도
할 수 있는 유일한 제안입니다.**

---

### 5 · 더 물어보기 (채팅 진입)

리포트 맨 아래에 **그 세션의 맥락을 물고** 채팅이 열립니다.
빈 입력창을 주지 않고, 이번 리포트에서 나온 질문 세 개를 칩으로 겁니다.

```
[ 화면과 거리를 어떻게 맞춰요? ]  [ 25분이 저한테 긴가요? ]  [ 기준을 다시 맞출까요? ]
```

채팅의 시스템 프롬프트는 리포트와 **같은 금칙어·같은 톤**을 씁니다.
의료 질문("목이 아파요")이 오면 진단하지 않고 전문가를 권합니다.
이건 회피가 아니라 정확한 답입니다.

## 4. 스키마 변경 제안

```ts
export const AiSessionReportSchema = z.object({
  headline: reportText(48),

  stats: z.array(z.object({           // 2번 칸 — 화면이 만들 수도 있지만
    label: reportText(12),            // AI가 순서를 정하게 두면 세션마다
    value: reportText(16),            // 가장 중요한 숫자가 앞에 옵니다
  }).strict()).length(3),

  observations: z.array(z.object({    // 3번 칸 — 새로 생김
    fact: reportText(60),             // 숫자에서 나온 사실
    read: reportText(90),             // AI의 해석
  }).strict()).max(2),                // ← min 이 없습니다. 비울 수 있어야 합니다

  nextAction: z.object({
    title: reportText(24),
    instruction: reportText(80),
    because: reportText(60),          // 새로 생김 — 어느 관찰에서 나왔나
    durationMinutes: z.number().int().min(1).max(5),
  }).strict(),

  followUps: z.array(reportText(28)).max(3),   // 5번 칸 칩
}).strict()
```

기존 `reflection`(160자)과 `highlights[3]`은 **없어집니다.**
`reflection` 은 사실과 해석이 한 덩어리라 어디까지가 측정인지 알 수 없었고,
`highlights` 는 길이가 정확히 3으로 고정돼 있어 할 말이 둘뿐인 세션에서
AI가 세 번째를 지어내게 만들었습니다.

`observations.max(2)` 에 `min` 을 두지 않은 것이 이 스키마에서 가장
중요한 한 줄입니다.

## 5. 열어 둔 것 / 결정이 필요한 것

| 항목 | 왜 아직 안 정했나 |
|---|---|
| 세션 간 비교 ("지난주보다") | 세션 기록이 기기에만 남아 서버가 지난주를 모릅니다. 클라이언트가 비교값을 계산해 입력에 넣을지 결정 필요 |
| 리포트 캐싱 | 같은 세션을 두 번 열면 두 번 부릅니다. 결과를 `localStorage` 에 붙일지 |
| 실패 시 | 키가 없거나 Gemini 가 죽으면 지금은 화면이 빕니다. 로컬 문장(현재 `composeReport`)으로 떨어질지 |
| 언어 | 지금은 한국어 고정 |

## 6. 확인이 필요합니다

**팀원이 넣었다는 Gemini API 키를 제가 확인하거나 사용하려면 말씀해
주세요.** 키는 Vercel 대시보드에만 있어야 하고
(`docs/ARCHITECTURE.md`), 이 저장소나 프론트엔드에 들어가면 안 됩니다.
지금 상태에서 제가 확인한 것은 `AI_REPORT_ENABLED`,
`VITE_ENABLE_AI_REPORT`, `GEMINI_API_KEY` 세 개가 **모두 있어야** 기능이
켜진다는 코드 사실뿐이고, 실제 키 존재 여부는 확인하지 않았습니다.
