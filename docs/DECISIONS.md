# DECISIONS

마지막 갱신: 2026-08-11

이 문서는 현재 작업자가 알아야 할 주요 의사결정을 요약합니다. 더 오래된 세부 결정은 `docs/20_DECISION_LOG.md`에 남아 있습니다. 실제 구현 판단은 현재 코드, migration, 최신 인수인계 문서를 우선합니다.

## D-001. 제품의 핵심은 자세 회복 습관이다

- 결정: 게임 요소가 늘어나도 자세 관리와 회복 흐름을 1순위로 둔다.
- 대안: 순수 게임형 서비스로 전환
- 이유: UpRight Now의 차별점은 웹캠 기반 개인 기준 자세 회복에 있다.
- 재검토: 픽셀 월드가 커질수록 자세 기능이 묻히지 않도록 홈과 세션 UI 우선순위를 계속 점검한다.

## D-002. 카메라 프레임과 자세 좌표는 서버로 보내지 않는다

- 결정: 카메라 영상, 이미지, 프레임, 랜드마크 원본, 자세 좌표를 저장하거나 전송하지 않는다.
- 대안: 서버 분석 또는 리플레이 저장
- 이유: 개인정보 위험이 크고, 현재 기능은 온디바이스 판정으로 충분하다.
- 재검토: AI 리포트가 확장되더라도 원문 영상·좌표 없이 요약 이벤트만 사용하는 원칙을 유지한다.

## D-003. Supabase는 데이터와 실시간 동기화의 기준이다

- 결정: 친구 방, 캠퍼스 인증, 캠퍼스 기여, 성장 보상은 Supabase migration과 RPC를 통해 관리한다.
- 대안: localStorage만 사용하거나 클라이언트에서 직접 점수 계산
- 이유: 여러 사용자와 학교 단위 경쟁을 다루려면 서버 기준 원장과 RLS가 필요하다.
- 재검토: 데이터가 복잡해지면 Supabase RPC 이름과 권한 정책을 별도 문서로 더 엄격히 관리한다.

## D-004. 구조 변경은 SQL migration 파일로 남긴다

- 결정: Supabase SQL Editor에서 실행한 구조 변경은 `supabase/migrations/`에 SQL 파일로 남긴다.
- 대안: 대시보드에서 수동 변경 후 구두 공유
- 이유: 팀원 Supabase와 개인 Supabase를 나중에 맞추려면 재현 가능한 migration이 필요하다.
- 재검토: Supabase CLI 도입 여부를 검토할 수 있다.

## D-005. 학교 인증은 이메일 도메인 기반으로 시작한다

- 결정: 학교별 허용 이메일 도메인을 DB에 저장하고, Supabase Auth 이메일 링크로 인증한다.
- 대안: 학생증 이미지 업로드, 포털 OAuth, 수동 승인
- 이유: 구현 난이도와 개인정보 위험을 줄이면서 “인증된 학생만 기여” 조건을 만족한다.
- 재검토: 학교별 도메인이 여러 개이거나 졸업생/교직원 정책이 필요하면 도메인 테이블과 승인 흐름을 확장한다.

## D-006. 학교 선택은 검색형 UI로 한다

- 결정: 화면에 대학 목록을 모두 펼치지 않고, 지역 선택 후 대학을 검색해서 고른다.
- 대안: 카드 목록 전체 노출
- 이유: 서울 소재 대학 수가 늘어나면 전체 목록은 가독성이 떨어진다.
- 재검토: 사용자가 직접 추가한 학교를 어떻게 검수할지 운영 정책이 필요하다.

## D-007. 학교 색상은 전역 테마로 반영한다

- 결정: 학교 선택 후 주요 CTA, 선택 테두리, 배지, 캠퍼스 UI에 학교 대표 색을 반영한다.
- 대안: 앱 고정 핑크색 유지
- 이유: 학교 소속감과 캠퍼스 경쟁 느낌을 강화한다.
- 재검토: 공식 로고·마스코트는 무단 사용하지 않는다. 색상도 공식성 표현을 피하고 “프로토타입 프리셋”으로 안내한다.

## D-008. 캠퍼스 영토전은 자치구 점령 모델로 전환한다

- 결정: 네모 grid가 아니라 서울 자치구 단위로 점령을 표현한다.
- 대안: 12×8 사각 grid 유지
- 이유: 사용자가 원한 것은 “서울대가 관악구를 점령” 같은 위치 기반 경쟁이다.
- 재검토: 현재 지도는 정확한 행정경계 데이터가 아니므로 공식 GeoJSON/SVG 기반으로 교체해야 한다.

## D-009. 영토전과 랭킹은 점수 원장 기반으로 계산한다

- 결정: 개인 기여도, 학교 점수, 시즌 점수, 자치구 소유권은 서버 데이터를 기준으로 계산한다.
- 대안: 화면에서 계산하거나 localStorage에 저장
- 이유: 여러 사용자 간 경쟁에서 조작과 불일치를 줄여야 한다.
- 재검토: 공격·방어 점수, 점령 임계값, 시즌 초기화 정책은 운영 데이터가 쌓인 뒤 조정한다.

## D-010. 학교별 참여 인원 보정점수를 둔다

- 결정: 랭킹 표시에는 `총 기여도 / sqrt(활성 참여자 수)` 형태의 보정점수를 적용한다.
- 대안: 총점만 사용
- 이유: 참여자 수가 많은 학교가 항상 유리해지는 문제를 완화한다.
- 재검토: 실제 데이터로 보정 강도가 과하거나 약한지 확인하고 계수화한다.

## D-011. 성장 XP는 차감하지 않는다

- 결정: 이미 얻은 장기 XP는 깎지 않는다. 실패 상황은 “보상 미지급”으로 처리한다.
- 대안: 나쁜 자세나 중도 종료 시 XP 차감
- 이유: 누적 성장 캐릭터가 퇴화하면 동기부여가 꺾이고 제품 톤과 맞지 않는다.
- 재검토: 필요하면 장기 XP가 아니라 시즌성 보너스나 캠퍼스 기여도에만 감점을 적용한다.

## D-012. 성장 보상은 서버가 금액을 결정한다

- 결정: 클라이언트는 이벤트 종류와 멱등 키만 보내고, XP·포인트 금액은 서버 규칙이 정한다.
- 대안: 클라이언트에서 XP·포인트를 계산해 전송
- 이유: 보상 조작과 버전 불일치를 막는다.
- 재검토: 기존 로컬 성장 데이터를 서버로 이관할지 정책 결정이 필요하다.

## D-013. 픽셀 월드는 기존 캠퍼스와 분리해서 시작한다

- 결정: 기존 `/campus` 영토전 화면은 유지하고, 픽셀 메타버스는 `/campus/world`에서 시작한다.
- 대안: 기존 캠퍼스 화면을 한 번에 픽셀 월드로 교체
- 이유: 안정적인 기존 기능을 보존하면서 새 게임 루프를 실험할 수 있다.
- 재검토: 픽셀 월드가 안정되면 캠퍼스 진입점을 재설계할 수 있다.

## D-014. 픽셀 월드는 Phaser + React 조합으로 구현한다

- 결정: React가 페이지·UI·접근성을 담당하고 Phaser가 월드 캔버스·이동·충돌·애니메이션을 담당한다.
- 대안: React DOM만으로 구현, Canvas 직접 구현, 외부 메타버스 서비스 삽입
- 이유: 키보드 이동, 충돌, 애니메이션에는 게임 엔진이 적합하고, 기존 앱 라우팅과 UI는 React가 유지하기 좋다.
- 재검토: 모바일 조작, 접근성, 번들 크기, 성능을 확인해야 한다.

## D-015. 픽셀 에셋은 직접 제작하거나 라이선스가 명확해야 한다

- 결정: 참고 이미지나 외부 게임 에셋을 그대로 복사하지 않는다.
- 대안: Stardew Valley, ZEP, SkyOffice류 에셋을 그대로 사용
- 이유: 저작권 위험이 크다.
- 재검토: 에셋 제작 파이프라인과 캐릭터 포맷을 확정해야 한다.

## D-016. 자유 채팅은 후순위다

- 결정: 초기에는 채팅보다 월드 기본기, 랭킹, 보상 구조를 우선한다.
- 대안: 바로 자유 채팅 구현
- 이유: 자유 채팅은 신고, 차단, 욕설 필터, 개인정보 노출, 운영 정책이 필요하다.
- 재검토: 친구 방 또는 공용 광장에 채팅을 넣기 전 moderation 정책을 정한다.

## D-017. 팀원/개인 Supabase는 분리될 수 있다

- 결정: 팀원 운영 프로젝트와 개인 실험 프로젝트는 서로 다른 Supabase 값을 가질 수 있다.
- 대안: 모두 한 Supabase 프로젝트 공유
- 이유: 실험 중 데이터 구조 변경이 운영 DB에 영향을 주지 않게 한다.
- 재검토: 병합 전에는 migration 파일과 seed 정책을 맞춰야 한다.

## D-018. Vercel 프로젝트마다 환경변수를 따로 설정한다

- 결정: 새 Vercel 프로젝트를 만들면 `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`를 직접 넣고 redeploy한다.
- 대안: 기존 팀원 Vercel 프로젝트 값을 그대로 사용
- 이유: 배포 사이트가 어떤 Supabase에 연결되는지 명확해야 이메일 인증과 DB가 꼬이지 않는다.
- 재검토: 팀 배포와 개인 배포를 문서화하고, production 권한을 누가 관리할지 정한다.

## D-019. 문서 인수인계는 최신 요약과 과거 기록을 분리한다

- 결정: 새 계정용 최신 문서는 `CODEX_HANDOFF`, `ARCHITECTURE`, `DECISIONS`로 분리하고, 기존 `AI_HANDOFF`와 `20_DECISION_LOG`는 상세 과거 기록으로 둔다.
- 대안: 기존 문서 하나에 계속 덧붙이기
- 이유: 새 작업자가 읽어야 할 최소 맥락과 과거 세부 내역을 분리해야 빠르게 시작할 수 있다.
- 재검토: 큰 기능이 merge될 때마다 세 문서를 함께 갱신한다.
