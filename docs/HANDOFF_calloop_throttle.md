# 팀원 전달용 — 월드 렉 수정 (calLoop 스로틀)

아래 프롬프트를 그대로 복사해서 Claude Code 에 붙여넣으면 됩니다.
브랜치가 달라도 같은 코드에서 갈라진 것이라 그대로 적용됩니다.

---

## 복사해서 쓸 프롬프트

```
prototypes/openworld/index.html 의 월드가 실사용에서 렉이 걸립니다.
원인은 이미 특정됐으니 확인하고 고쳐 주세요.

[원인]
이 파일은 자세 추론(POSE.detect)을 두 루프에서 부르는데, 한쪽만 호출
빈도를 자릅니다.

  · poseLoop  — 앉아 있는 동안. `if (now - lastDetect < 66) return;` 있음 (~15fps)
  · calLoop   — 기준 잡는 10초.  같은 줄이 없음 → 매 rAF, 초당 60회

poseLoop 의 주석이 왜 잘라야 하는지 이미 적어 두었습니다:
"동기 추론 2개(pose+face)가 월드 렌더와 같은 rAF 를 나눠 쓰게 됐습니다
 — 안 자르면 메인스레드가 마릅니다."
calLoop 이 정확히 그 상태입니다.

[측정된 근거]
배포본 계측: 22초 동안 detect 641회 = 초당 29회 (의도 15회).
이 숫자도 과소평가입니다 — 프로파일링 브라우저의 가짜 카메라에는 사람이
없어서 랜드마크 모델이 아예 안 돕니다.
실제 사람이 있으면 한 프레임 88.8ms (Intel Iris Xe, IMAGE 모드, 60회 중앙값).
60fps 로 부르면 1초에 5.3초어치를 시키는 셈이라 렌더가 설 자리가 없습니다.

[고칠 것]
calLoop 안, `const now = performance.now();` 다음에 poseLoop 과 **같은**
스로틀 두 줄을 넣습니다.

  if (now - lastDetect < 66) return;
  lastDetect = now;

lastDetect 는 poseLoop 과 같은 스코프의 모듈 변수라 그대로 씁니다.
두 루프는 서로 배타적입니다(startCalibrate 가 poseRunning 을 내림).
그래서 타임스탬프를 나눠도 안전하고, 오히려 전환 직후 한 프레임이
겹치는 것을 막아 줍니다.

왜 이 값이어야 하는지 주석으로 남겨 주세요 — 다음 사람이 또 지웁니다.

[건드리지 말 것]
· 66 이라는 값 (판정 품질은 그대로입니다. HOLD 가 경고 1.5초·굽음 5초라
  15fps 로도 충분합니다)
· prototypes/onboarding/index.html — 이미 같은 스로틀이 들어 있습니다
· 모델(pose_landmarker_full)과 라이브러리(tasks-vision@0.10.35) 버전

[검증]
고친 뒤 실제로 빈도가 내려갔는지 재 주세요. 눈으로는 안 보입니다.

1) 서버를 띄웁니다 (저장소 루트에서)
     npx http-server . -p 8177 -c-1

2) Playwright 로 POSE.detect 를 감싸 호출 횟수를 셉니다.
   가짜 카메라를 쓰고, 페이지를 연 뒤 startCalibrate() 를 직접 호출해
   10초쯤 두고 초당 호출 수를 계산합니다.

   기대값: 고치기 전 초당 약 29회 → 고친 뒤 약 14~15회

3) npm test 로 기존 테스트 28개가 그대로 통과하는지 봅니다.

숫자를 보고하고, 14~15회가 안 나오면 멈추고 알려 주세요.
```

## 같이 알아 두면 좋은 것

렌더 렉과 **별개로** 로딩도 무겁습니다. 배포본 계측에서

```
DOMContentLoaded 4,891ms
요청 226건 (이미지 192 · 스크립트 12 · 폰트 16)
```

이미지 192장은 스프라이트·아이템 에셋입니다. 스프라이트 시트로 묶으면
요청 수가 크게 줄어듭니다. 이번 수정 범위는 아니고, 별도 작업입니다.
